# 2026-11-19 工作日志

## RTK 连接时间长了数据卡住（还显示已连接，但数据不跳）修复

### 现象
连接 RTK 时间长了，定位数据卡住不更新，但「已连接」状态还在。两种连接方式（蓝牙/WiFi TCP）都会出现。

### 根因分析
1. **数据分发通道依赖 Activity 生命周期**：`tdyb-rtk` 插件的 `postToUi()` 用 `UTSAndroid.getUniActivity().runOnUiThread(...)` 把读线程的数据抛回主线程。长时间运行/App 前后台切换后，`getUniActivity()` 可能返回已失效的 Activity，任务投递到失效队列被丢弃 → 数据不再分发，页面数据卡住。
2. **socket.isConnected() 误报**：TCP 半关闭/对端掉线未发 FIN 时，`socket.isConnected()` 仍返回 true，导致 `connected` 一直显示"已连接"，无法察觉数据其实已经断了。

### 修复
1. **`uni_modules/tdyb-rtk/.../index.uts`**：`postToUi()` 改用全局主线程 `Handler(Looper.getMainLooper())`（新增 `mainHandler`/`getMainHandler()`），不依赖 Activity 生命周期，保证数据分发永远走主线程消息队列。新增 import `Handler`、`Looper`。
2. **`pages/rtk-setting/rtk-setting.uvue`**：新增「数据失活检测」：
   - `stopStaleWatch()`/`checkStale()`/`startStaleWatch()` 三个函数。
   - `checkStale()` 每 3 秒（`setInterval`）检查 `getLastFixAt()`，连接中且距上次 GGA 超过 15 秒 → 判定失活，主动断开本地 socket、清 UI、toast「连接已中断，请重新连接」。
   - `onShow` 里 `startStaleWatch()`，`onUnload` 里 `stopStaleWatch()`。
   - 阈值 15 秒（RTK 可能 5 秒/条慢推流，太短会误判）。

### 关键认知
- UTS 函数不提升，`stopStaleWatch` 必须定义在 `checkStale` 之前（`checkStale` 里调用了它）。
- `setInterval`/`clearInterval` 返回值类型是 `number | null`，与 `bridge/rtk.uts` 里 `autoReconnectTimer` 一致。

## RTK 数据卡住根治（第二轮：bridge 层全局自愈）

### 补充根因（第一轮只修了页面层，不够）
1. **读线程静默卡死**：TCP 无 keepalive，对端断电/热点休眠后连接半开，`readLine()` 永久阻塞不抛异常；蓝牙 SPP 超距同理。→ `lastFix` 永久不更新。
2. **`shouldUseRtk()` 被假连接骗过**：`rtkIsActive()` 只看 `socket.isConnected()`（本地没 close 就返回 true）→ 定位入口一直走 RTK 分支。
3. **`rtkOnce()` 超时不限龄兜底**：3 秒超时后无条件下发 `getLastFix()`（可能几小时前）→「点定位永远是同一个位置」。
4. **页面看门狗有盲区**：`checkStale` 只在 rtk-setting 页 onShow/onUnload 间运行，地图页无人检测。

### 修复（bridge/rtk.uts + index.uts）
1. **`rtkIsActive()` 新鲜度感知**：`isRtkConnected()` 且（无数据宽限 或 `Date.now()-getLastFixAt()<=10s`）。数据卡死 → 定位自动回退高德。
2. **`rtkOnce()` 兜底加新鲜度**：超时仅当 `lastFixFresh()`（≤10s）才回缓存，否则 replyError「RTK 数据已过期，正在重连」。
3. **全局自愈看门狗**：`tryAutoReconnect()` 开头新增 `healStaleConnection()`——已连接但 >20s 无新 GGA → 主动 close 两个 socket → 同轮走重连（rtkDevice 未删）。页面无关，蓝牙/WiFi 通吃。
4. **TCP 加固**：`connectTcp` 连接后 `setKeepAlive(true)` + `setTcpNoDelay(true)`。

### 阈值
- 新鲜度 10s（RTK 慢推流约 5s/条）；自愈 20s；页面 toast 15s（保留作快速 UI 反馈）。
- 全部改动需重新打基座验证。

## 第三轮：对齐旧插件 Lin-RtkManager（_rtk_decomp 反编译对比）

### 对比发现（旧插件为何能长连）
反编译文件：`D:\chen\TDYB\_rtk_decomp\wifi.txt`（WifiConnectManager）、`brtm.txt`（BluetoothRtkManager）。
1. **WiFi 网络绑定（核心差异）**：旧插件构造时 `ConnectivityManager.requestNetwork(NetworkRequest TRANSPORT_WIFI, callback)` 持有 `Network`，所有 socket（端口探测 + 正式连接）用 `wifiNetwork.getSocketFactory().createSocket()` 建——强制流量走 WiFi 接口。RTK 热点无互联网，Android 会把默认网络切到蜂窝；用默认网络建的 TCP 在系统网络切换后流量被黑洞（无 RST）→ readLine 永久阻塞、isConnected() 误报 → 数据卡住假连接。这是我们新插件卡死的主因。
2. **蓝牙读线程异常就地关连接**：旧插件 `readRtkData` 的 IOException → `closeBluetoothConnection()`，状态诚实。我们旧代码线程退出但 socket 不 close，isConnected() 继续误报。
3. **WiFi 读循环内自动重连**：捕获 "Software caused connection abort" → sleep(delay) → 循环重建 socket。这层我们用 bridge 的 healStaleConnection + 自动回连覆盖，未照搬。

### 本轮修改（index.uts）
1. 新增 import：ConnectivityManager/Network/NetworkCapabilities/NetworkRequest/NetworkCallback(`android.net.ConnectivityManager.NetworkCallback`)。
2. 模块级 `wifiNetwork`/`wifiNetworkRequested` + `WifiNetworkCallback`(onAvailable/onLost) + `ensureWifiNetworkBound()`（幂等）+ `createLanSocket()`（有 Network 用其 SocketFactory，否则退回普通 Socket）。
3. `scanTcpPort`/`scanSubnetForRtk`/`connectTcp` 入口调 ensureWifiNetworkBound；三处 `new Socket()` 改 `createLanSocket()`（仅 createLanSocket 内保留一处兜底）。
4. `NmeaReaderRunnable` 加 `onExit` 回调：读线程 finally 里 postToUi 执行——蓝牙传 closeBluetoothInternal、TCP 传 closeTcpInternal；catch 加 warn 日志。
5. `startReaderThread(input, label, onExit)` 签名变更，两个调用点已更新。

### 注意
- Kotlin/UTS 嵌套类 import 写法：`import NetworkCallback from 'android.net.ConnectivityManager.NetworkCallback'`。
- 需重新打基座验证；观察日志 `[tdyb-rtk] 已绑定 WiFi 网络` / `读取异常，连接已断开`。

## WiFi 设备列表「可连接」显示慢优化

### 原因
1. `scanTcpPort` 超时 2 秒：同网段预设中 IP 不存在/端口未开的都要等满 2s。
2. 列表排序用固定 `setTimeout(1500)` 干等，不跟随探测完成。
3. 徽标点亮依赖探测回调，被前两条拖慢。

### 修复
1. `index.uts` `TcpPortScanRunnable`：connect 超时 2000→600ms（局域网 RTT 毫秒级）。
2. `rtk-setting.uvue` `probePresets`：抽出 `sortConnectableFirst(list)`，探测回调计数 `finished>=pending` 时立即排序，删掉 1.5s 定时器。
- 注意：`sortConnectableFirst` 声明在 `probePresets` 之前（uvue setup 内局部函数不提升）。

## 云打包报错修复（2026-11-20）：staleTimer smart cast

- 报错：`rtk-setting.kt:311 Smart cast to 'Number' is impossible, because 'staleTimer' is a local variable that is mutated in a capturing closure`。
- 原因：`staleTimer` 是 setup 局部变量，被 `startStaleWatch` 的 setInterval 闭包捕获修改，`stopStaleWatch` 里 `if (staleTimer != null)` 无法 smart cast。
- 修复：`const t = staleTimer; if (t != null) { clearInterval(t); staleTimer = null }`——同 bridge/rtk.uts `stopAutoReconnect` 的既有模式（该文件注释里早写过这个坑）。
