## 一、现状（已核对代码）

### 1.1 旧壳 = uni-app（vue3 + App-Plus），不是 uni-app x

`10_思明数据采集/manifest.json`：`app-plus` + `vueVersion: "3"` + `compilerVersion: 3`，
页面是 `.vue/.nvue`，原生能力靠 4 个 `nativeplugins`（`uni.requireNativePlugin` + `plus.*`）。

| 旧壳组成 | 用途 | 在 uni-app x 里 |
|---|---|---|
| `pages/webView/webView.nvue` | `<web-view>` 容器 + `evalJS` 反向注入 | 需重写（web-view 能力不同） |
| `nativeplugins/Amap-Location` | 高德定位 SDK（aar，`cn.lincq.amaplocation.FunAmapLocationModule`） | **nativeplugin 不能用**，需 UTS 重写 |
| `nativeplugins/Lin-RtkManager` | 蓝牙/TCP 连 RTK，读 NMEA GGA | **nativeplugin 不能用**，需 UTS 重写（若还要 RTK） |
| `nativeplugins/Lin-Accessibility` / `Lin-Alive` | 无障碍/悬浮窗/保活 | 大概率不需要，去留先确认 |
| `utils/app/permission.js`、`pages/permissions/*` | `plus.android.requestPermissions` / 跳系统设置 | `plus.*` 不可用，需 UTS/uni API 重写 |

### 1.2 前端已有的桥接协议（这是最重要的现有资产）

`TDYB_VUE/frontend/src/bridge/location.ts` 已经抽象好了，**协议是：**

```
页面 → 壳:  { method, message, key }        key = 一次性回调变量名
壳 → 页面:  window[key] = JSON字符串        （旧壳用 evalJS 执行这句）
```

页面实际用到 5 个方法：

| method | 语义 | 现前端调用点 |
|---|---|---|
| `getPreciseLocation` | 单次高精度定位（wgs84） | `CollectionView.locateOnce()` |
| `getLocationQuickly` | 单次快速定位（兜底） | 同上，失败兜底 |
| `startGetLocationService` | **持续定位流**，每来一条回传一次 | `useAutoRecord.start()` |
| `closeGetLocationService` | 停止持续定位 | `useAutoRecord.stop()` |
| `openLocationSetting` | 打开壳的 RTK/定位设置页 | 暂无调用（保留） |

`useAutoRecord` 收到后自己再做 1s/0.5m 节流，所以**壳回传频率可以比前端需求更粗**。

### 1.3 新壳现状

`D:\chen\TDYB\TDYB` 是 HBuilderX 新建的 uni-app x 空模板（`main.uts` / `App.uvue` / 只有 `pages/index`），

## 二、先定一个关键判断：要不要全量 uni-app x

uni-app x 在 App 端的原生能力边界（这是本项目的真正风险点，不是"要不要用 vue"）：

1. **没有 `plus.*`**：权限、系统设置跳转、后台服务都要 UTS 重写。
2. **没有 `uni.requireNativePlugin`**：旧的 4 个 aar 插件**全部失效**，高德定位必须走 UTS 插件。
3. **`<web-view>` 与网页的双向通信能力比 uni-app 弱**：`evalJs`（壳→页）在 App-Android 可用；
   页→壳 的 `@message` + JS SDK 通道**必须真机先验证**，不稳就要走兜底方案（见 3.2）。
4. 生态插件少，出问题要自己啃 Android。

结论：**不要在没验证通信通道前就全量迁移**。用下面的"三段式"排期。

## 3.1 通信层设计（已定稿，按 uni-app x 官方签名）

**结论：走官方 `@message` + `evalJS`，没有任何注入/轮询。**

从 HBuilderX 自带类型定义确认的事实（`builtin-dts/.../uni-app-x/types/native/IUniElement.d.ts`）：

| 项 | 官方签名 | 影响 |
|---|---|---|
| 壳 → 页 | `evalJS(js: string): void` | 单向，**无返回值/回调** → 壳不能主动取网页数据 |
| 页 → 壳 | 网页调 web-view 注入的 `window.__uniapp_x_postMessage({data})`；壳侧 `@message` 的 `event.detail.data` 是 `Array<UTSJSONObject>` | 网页必须发**对象**，不能发字符串 |
| 页面加载完成 | `@load` 事件 | 没有 `pagefinish` 事件 |

```
┌───────────── Vue 页面（WebView） ─────────────┐
│ bridge/location.ts                            │
│   postMessageToApp({method,message,key})      │
│        │                                      │
│        ▼ window.__uniapp_x_postMessage({data})│
│   window[key] = '...'  ←───────────────┐      │
└────────────────────────────────────────┼──────┘
                                          │
┌──────────── 壳（uni-app x） ────────────┴──────┐
│ <web-view @message> detail.data[] → dispatch   │
│ LocationService（UTS 高德）→ 按 interval 节流   │
│ evalJS(`window["key"]="<json>"`)                │
└─────────────────────────────────────────────────┘
```

### 3.2 被否决的方案（留作记录）

| 方案 | 为什么不用 |
|---|---|
| 壳用 `evalJs` 轮询网页队列 | `evalJS` 根本没有返回值，物理上做不到 |
| 自己注入 `uni.postMessage` 垫片 | 网页本来就拿到了 web-view 注入的 `window.__uniapp_x_`，前端直接调它就行；垫片只会多一层、还可能覆盖页面自己的 `uni` 对象（已删除） |
| 本地 HTTP / WebSocket 回调 | 要额外起服务，复杂度远超收益 |

### 3.3 方案 B（回退路线）：壳继续用 uni-app（vue3）

如果 uni-app x 这条路彻底走不通（编译平台问题无法解决），**最省钱的是**：
保留 uni-app（vue3）壳，只把 `webSrc` 从旧原生页改成新前端地址。
现有 1900 行壳代码、4 个原生插件、`evalJS` 协议全部复用，**改动量 = 改一个 URL + 删无用页面**。

> 建议决策线：阶段 0 花 2 天；若 2 天内通信通道打不通，就切方案 B，不要在 uni-app x 上做无底洞。

## 四、定位能力设计（壳侧）

### 4.1 前端要什么，壳就给什么

```ts
// 页面 → 壳 持续定位（前端传节奏）
{ method: 'startGetLocationService',
  message: { interval: 1000,        // ms，前端希望的回传节奏（钳制 1000~10000）
             coordType: 'wgs84',    // wgs84 | gcj02，默认 wgs84
             needAddress: false,    // 是否需要地址（反地理编码，费流量）
             distanceFilter: 0 },
  key: '__appid_xxx' }

// 壳 → 页面 每条一次（字段对齐 normalizeLocation）
{ longitude, latitude, altitude, accuracy,
  fixStatus: 'gps' | 'fixed' | 'float',   // 手机定位固定 'gps'
  coordType: 'wgs84', timestamp,
  speed, bearing, locationType, raw? }
```

**回传节流策略（壳内做，避免桥被淹）**：高德 SDK 以 `interval` 采样，
壳按 `interval` 合并 + 位移/精度门限（如 accuracy 变差 >20% 或位移 >0.3m 才再发）；
`onHide` 时降频到 5s 并保持（后台定位权限允许），`onUnload` 必须 stop。

### 4.2 高德 SDK 怎么进 uni-app x

- 路线：`uni_modules/tdyb-location/utssdk/app-android/index.uts`，
  用 `UTSAndroid.importClass("com.amap.api.location.AMapLocationClient")` 封装
  `start/stop/once`，`app-android/config.json` 声明依赖。
- Key：已改为新申请的 Android key，写在
  `uni_modules/tdyb-amap-location/utssdk/app-android/AndroidManifest.xml` 的
  `com.amap.api.v2.apikey`；包名 `com.kingtop.xasjcj` + 云证书 SHA1 必须在高德控制台绑死。
  （旧壳 manifest 里的 `amap_18396195512BEgoeyift` 是 key 名称，不是 key 本身，别混。）
- 权限（Android 11+ 必配）：`ACCESS_FINE_LOCATION`、`ACCESS_COARSE_LOCATION`、
  持续定位还需 `ACCESS_BACKGROUND_LOCATION` + 前台服务（`FOREGROUND_SERVICE_LOCATION`）。
  uni-app x 里用 `uni.requestPermissions(["android.permission.ACCESS_FINE_LOCATION"])`，
  系统设置跳转要 UTS 写 Intent。

### 4.3 ⚠️ RTK 与前端精度门限的冲突（必须现在定）

前端 `useAutoRecord` 默认 `maxAccuracy = 0.05`（5cm），`isFixedSolution` 用它过滤：

```ts
// TDYB_VUE/frontend/src/composables/useAutoRecord.ts:30
const maxAccuracy = options?.maxAccuracy ?? 0.05;
```

手机高德定位精度通常 5~30m，**永远过不了这个门限 → 自动记录会一条都不出**。
两条路选一条：

- 要 RTK：UTS 重写 `Lin-RtkManager`（蓝牙/TCP + NMEA GGA 解析），复用旧 `parse-positioning.js`，`fixStatus` 给 `fixed/float`。
- 不要 RTK：把 `useAutoRecord` 的 `maxAccuracy` 按模式传（手机模式 20~50m），或 `isFixedSolution` 增加 `mode` 参数。

**这个决定影响壳要不要做蓝牙，请先确认。**

## 五、部署侧必须一起改的点

1. **SPA history 路由**：Vue 是 `history` 模式，Nginx 必须 `try_files $uri /index.html`，否则 web-view 刷新/深链 404。
2. **`/api` 与 `/geoserver` 反代**：沿用 `vite.config.ts` 里那三条，生产由 Nginx 同域转发（避免 CORS 和 web-view 的混合内容限制）。
3. **HTTPS 混用**：web-view 页面若走 https，页面内所有 `http://192.168.x` 的 GeoServer/WMS 会被拦（Android WebView 默认阻止 mixed content）。**统一走 https 或统一内网 http**，不要混。
4. **`<web-view>` 首屏白屏**：靠 `@load` 事件判断加载完成；`@error` 走离线页（旧壳 `pages/error` 可参考）。
5. **返回键**：网页是自己的 SPA，壳拦截返回键时要先 `window.history.back()`（通过 evalJs 调页面方法），只有到栈底才退出——旧壳 `onBackPress` 里调 `getAppHdMsg()` 的思路可以沿用（改成调页面导出的 `__onNativeBack()`）。
6. **Cookie/localStorage**：uni-app x web-view 用系统 WebView，`localStorage` 在 App 内是共享的，登录态没问题；但如果前端用了 `sessionStorage` 或第三方 cookie，要单独验证。
